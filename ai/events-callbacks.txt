EVENTS & CALLBACKS
==================

THE INTERACTION MODEL
---------------------
- Events: kebab-case, present tense, `bubbles: true`, NOT composed. A listener
  on <web-dropzone> or any light-DOM ancestor receives them; they do not cross
  out of an enclosing shadow root (listen on the element itself there).
- Every event has a camelCase `on*` twin property, called FIRST with the same
  detail object, then the DOM event is dispatched:
      dz.onFileAdd = ({ file }) => ...      // same as addEventListener('file-add')
- Every event detail and every callback ctx carries two NON-enumerable fields:
      controller  the DropzoneController (=== dz.controller)
      element     the <web-dropzone> host
  Destructuring works; JSON.stringify / Object.keys / spread see only the data
  ({ ...detail } drops them).
- Callbacks take ONE ctx argument. before*Callbacks may be async; returning
  `false` cancels; a throw also cancels (logged).
- Callbacks are property-only (no attribute). Events are for observing;
  *Callback hooks affect state (gate, transform, upload, render).

EVENT TABLE (<web-dropzone>)
----------------------------
| Event                | Twin                 | Detail                                        |
|----------------------|----------------------|-----------------------------------------------|
| file-add             | onFileAdd            | { file }                                      |
| file-remove          | onFileRemove         | { file }                                      |
| change               | onChange             | { files }                                     |
| files-change         | onFilesChange        | { changedIds, files }                         |
| file-reject         | onFileReject        | { rejectedFiles: [{ file, validation }] }     |
| file-progress        | onFileProgress       | { id, progress, status, file }                |
| file-status-change   | onFileStatusChange   | { id, oldStatus, newStatus, file }          |
| file-update          | onFileUpdate         | { file }                                      |
| file-retry           | onFileRetry          | { file }                                      |
| file-upload | onFileUpload | { file }                                      |
| file-cancel          | onFileCancel         | { file, result, uploadedBytes, metadata }     |
| file-delete          | onFileDelete         | { file }                                      |
| overlay-enter        | onOverlayEnter       | { overlayElement }                            |
| overlay-leave        | onOverlayLeave       | { overlayElement }                            |
| ready                | onReady              | context only (controller, element)            |

`file` is a FileState (id, file, name, size, type, status, progress, error,
previewUrl, downloadUrl, metadata, ...). In file-reject, `file` is the native
File (it never entered the list).

WHEN EACH FIRES
---------------
file-add            per accepted file, after validation and beforeFilesAddCallback.
file-remove         per file leaving the list (remove, clear, timeout-remove,
                    mode-flip rebuild).
change              once per add batch / removal batch. Re-stamps the form value
                    before listeners run.
files-change        at most once per animation frame: ids touched since the last
                    tick (alive or removed) + full snapshot. Best channel for
                    reactive renderers.
file-reject        validation failures, or a beforeFilesAddCallback veto
                    (code 'rejected'). One event per batch.
file-progress       progress value changed (also the 0->100 jump on complete).
                    Rate-limited by progress-throttle.
file-status-change  oldStatus !== newStatus guaranteed.
file-update         a field other than progress/status changed: previewUrl
                    generated, or the upload result merged (metadata,
                    downloadUrl, previewUrl, name).
file-retry          a failed / cancelled file was re-queued (status already 'pending').
file-upload  uploadFileCallback resolved.
file-cancel         a cancel FINISHED (see below).
file-remove vs file-delete: file-remove = the file left the LIST (local:
                    row X, removeFile(s), Clear all, single-file replace, mode
                    flip). file-delete = SERVER state, see next line.
file-delete         fires together with file-remove when the removed file has
                    server-side state: status 'complete', OR non-empty metadata
                    (e.g. stashed via ctx.setMetadata during a partial upload).
                    Wire your server DELETE here.
overlay-enter/leave a drag entered / left the overlay-target overlay.
ready               core: fired ONCE, after the first build (dz.controller is
                    live). Host gets the `ready` attribute + :state(ready);
                    dz.whenReady() is the promise form. A mode-flip rebuild or a
                    DOM move never re-fires it.

FILE-CANCEL
-----------
detail: {
  file,             // FileState after the cancel
  result,           // 'cancelled' | 'timeout-error' | 'timeout-remove'
  uploadedBytes,    // bytes reported when the cancel finished
  metadata          // what the handler stashed via ctx.setMetadata, or undefined
}

result:
  cancelled       handler settled within cancel-timeout (or nothing was running);
                  row stays, status 'cancelled', retryable
  timeout-error   handler ignored its signal; status 'error',
                  file.error === 'cancel-timeout', retryable
  timeout-remove  same, with cancel-timeout-behavior="remove": the file was
                  removed (file-remove, and file-delete if metadata, fired BEFORE
                  this event)

Server-side cleanup of a partial upload is the APP's job:

dz.onFileCancel = async ({ file, result, metadata }) => {
  if (result === 'timeout-remove') return;      // file-delete already covered it
  const url = metadata?.uploadUrl;              // e.g. tus upload URL
  if (url) await fetch(url, { method: 'DELETE', headers: { 'Tus-Resumable': '1.0.0' } });
};

dz.onFileDelete = async ({ file }) => {
  const url = file.metadata?.uploadUrl;
  const id = file.metadata?.serverId;
  if (url) await fetch(url, { method: 'DELETE' });
  else if (id) await fetch(`/api/files/${id}`, { method: 'DELETE' });
};

Note: a cancelled row keeps its metadata. If the user later removes it,
file-delete fires again for the same metadata - make DELETE idempotent (404 ok)
or track already-cleaned URLs.

GATES IN DETAIL
---------------
beforeFilesAddCallback - once per add batch, AFTER validation:
  false     -> files reported in file-reject with code 'rejected'
  File[]    -> replaces the batch (validated again; the hook is not re-run)
  nothing   -> continue
While its promise is pending, files are NOT in the list (no file-add).

dz.beforeFilesAddCallback = async ({ files, existingFiles }) => {
  if (!(await confirmDialog(`Add ${files.length} file(s)?`))) return false;
  return files.filter(f => !f.name.startsWith('~$'));   // drop Office temp files
};

beforeFilesRemoveCallback - user removals (row Remove, popover "Clear all");
programmatic removeFile / removeFiles / clear only with { confirm: true }
(asked ONCE per batch). `files` = leaving, `allFiles` = current list.

dz.beforeFilesRemoveCallback = ({ files }) =>
  files.some(f => f.status === 'complete') ? confirm('Remove uploaded files?') || false : undefined;

beforeFilesCancelCallback - cancelFile(id) / row Cancel ask with [file];
cancelAll() / "Cancel all" ask ONCE with every file being cancelled.
NOT asked for internal cancels (Remove on a running file, element removal).

dz.beforeFilesCancelCallback = async ({ files }) =>
  (await confirmDialog(`Stop ${files.length} upload(s)?`)) ? undefined : false;

Only `false` cancels - undefined / true / anything else continues.

USING controller FROM A CALLBACK
--------------------------------
dz.onFileAdd = ({ file, controller }) => {
  if (controller.getFiles().length > 20) controller.removeFile(file.id);
};

dz.onFileReject = ({ rejectedFiles, element }) => {
  element.dispatchEvent(new CustomEvent('toast', { bubbles: true,
    detail: rejectedFiles.map(r => `${r.file.name}: ${r.validation.error}`) }));
};

SATELLITE EVENTS
----------------
Dispatched on the satellite itself (bubbles, not composed); detail carries the
BOUND STORE's controller / element:
  <web-dropzone-list> summary-activate   popover appearance: summary line activated
  <web-dropzone-list> queue-open         rolling appearance: queue button clicked
Every satellite (a core BlissElement) also fires core's `ready` (once, after
its first build; onReady twin) and `input-rejected` (an invalid value - e.g. an
unknown enum - was refused; the previous value stays) on itself.
Structural rows: file-row-update ({ file }) on the element a
renderFileItemCallback returned.

INTERNAL (NOT PUBLIC)
---------------------
dz-config-changed, dz-reorder, dz:overlay-drag-ended are internal signals.
Do not depend on them.

ORDERING NOTES
--------------
- Add: file-add (per file) -> change -> file-reject (if any) -> (auto-upload starts).
- Remove: [cancel running uploads first] -> file-remove (+ file-delete) per file
  -> change.
- Upload success: [file-update if result merged] -> file-status-change
  (uploading->complete) + file-progress -> file-upload.
- files-change is asynchronous (next frame); everything else is synchronous
  with the state change.

TYPES
-----
